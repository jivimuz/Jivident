# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Jivident is a Laravel 12 clinic/dental-practice management system — originally patient registration/queue/examination/billing/inventory, now grown into a broader clinic ERP: pharmacy POS, payroll (PPh21/BPJS), employee scheduling & leave, doctor appointment booking, multi-branch (`Klien`), and financial/clinical/HR reporting. It's a classic server-rendered Blade admin app (jQuery + Bootstrap admin template), not an SPA — there is no API layer for a separate frontend.

## Commands

```bash
# First-time setup (creates .env, generates key, migrates)
composer setup

# Local dev — runs php artisan serve, queue:listen, and pail (log tailing) concurrently
composer dev

# Run the full test suite (clears config cache first)
composer test
# equivalent to:
php artisan test

# Run a single test file / method
php artisan test tests/Unit/ProductQtyHelperTest.php
php artisan test --filter=test_stock_out_fefo_consumes_earliest_expiring_lot_first

# Lint / format PHP (Laravel Pint)
vendor/bin/pint
vendor/bin/pint --test   # check only, no write

# DB
php artisan migrate
php artisan migrate:fresh --seed

# Demo transactional data (patient visits, POS sales, rawat inap, appointment) —
# NOT run by the above; separate on purpose, see the Seeders note below.
php artisan db:seed --class=TransactionalSeeder
```

There is no frontend build step — see the Vite note below. `tests/` has broad feature/unit coverage now (28 test files, 131+ tests) spanning most controllers added or touched since the original audit (TODO.md) — patient/billing helpers, license gate, POS, payroll, appointment booking, multi-branch, reporting, etc. Older parts of the app predating that audit (odontogram, SOAPE, prescriptions, most of `PatientController`/`PemeriksaanController`) still have little to no test coverage — be cautious making changes there without adding tests first.

## Architecture

**All business logic lives under one controller namespace:** `App\Http\Controllers\Website\*`. Routes are defined entirely in [routes/web.php](routes/web.php) (no `api.php`), grouped by feature prefix (`patient`, `pemeriksaan`, `transaction`, `billing`, `product`, `employees`, etc.), each wrapped in `auth` + a per-feature `checkAccess:<CODE>` middleware group, and the whole authenticated group is throttled (`throttle:300,1`).

**Access control is module-code based, not role-based.** `App\Http\Middleware\CheckModuleAccess` (aliased as `checkAccess`) reads the comma-separated `access` column on the logged-in `User` (a list of `m_modules` IDs) and checks it against the module `code` passed to the middleware (e.g. `checkAccess:PA` for Patient, `checkAccess:MTU` for user management, `checkAccess:DPP` for pemeriksaan). See [app/Models/Module.php](app/Models/Module.php) and [app/Http/Controllers/Website/ModuleController.php](app/Http/Controllers/Website/ModuleController.php) for how access lists are assigned per user.

**Fullscreen pages (no sidebar):** [layout/fullscreen.blade.php](resources/views/layout/fullscreen.blade.php) is a layout variant for pages that want their own full-screen UI instead of the admin sidebar/topcontent chrome — first used by POS Apotek (`pos/index.blade.php`, `@extends('layout/fullscreen')`), requested by the app owner so the cashier screen isn't cramped by the sidebar. It still `@include`s the same `layout/header`/`layout/footer` partials as `layout/main` (so jQuery/Bootstrap/DataTables/SweetAlert2/Select2/`Toast`/the profile password & signature modals all work identically, zero duplication) — it just omits `layout/navbar` and `layout/topcontent`, and its content isn't wrapped in the `.app-content` class (which `style.css` reserves `padding-left: var(--sidebar-width)` for — keeping that class without an actual sidebar would leave a dead gap). Since removing the sidebar also removes the only way to navigate elsewhere or log out, a page using this layout should build its own slim top bar (logo + title + a link back to `/` + a logout link with **`data-turbo="false"`**, matching the one in `topcontent.blade.php` — logout is a plain GET with a side effect, so it must bypass Turbo's hover-prefetch same as the main app's). Reach for this layout for any other "wants its own fullscreen workspace" page (e.g. a future kiosk-style check-in screen); for anything that still belongs in the normal admin chrome, keep using `layout/main`. **A page on this layout is linked from the "Menu Lain" dropdown in `topcontent.blade.php` (visible on every `layout/main` page's topbar), not from a sidebar `Module` row** — that's how Monitor Antrian and Portal Pasien are already reached (neither has a `Module` row at all), and POS's own pre-existing sidebar entry (code `POS`) was deactivated (`isactive = false`, see [2026_03_23_000000_deactivate_pos_sidebar_module.php](database/migrations/2026_03_23_000000_deactivate_pos_sidebar_module.php)) to match once it moved to this layout — landing on a fullscreen page *from* the sidebar, with no sidebar to click back into, read as redundant/odd now that "Menu Lain" already covers it. Deactivating rather than deleting the row matters: `CheckModuleAccess` looks the module up by `code` regardless of `isactive` (that flag only filters `navbar.blade.php`'s own listing query), so deleting it instead would 403 everyone out via `checkAccess:POS`. **Gotcha found shipping the POS page (showed up as a broken/squashed layout, not an error):** `.app-wrapper` itself is `display: flex`, and every one of `layout/main`'s other direct children (`nav`, the copyright `<footer>`, `.go-top`, the boot-splash `.loader-wrapper`) escapes that flex sizing via `position: fixed`/`absolute` rather than relying on flex-item stretch — `.app-content` is the only normal-flow flex child, and it works because it explicitly sets `width: 100%; height: 100%`. A fullscreen-layout page's own root content div is now *also* a normal-flow flex child of `.app-wrapper` with no sibling competing for space, so without an explicit width it can size to content instead of filling the viewport — Bootstrap's percentage-based `.col-*` grid inside it then computes against that wrong width and the whole page looks cramped/broken. Fix (and the pattern to copy for the next fullscreen page): give the page's root content div `position: fixed; inset: 0;` with `width/height: 100%`, taking it out of `.app-wrapper`'s flex flow entirely the same way `nav`/`footer`/`.go-top` do, and a `z-index` above the fixed footer (1000) and `.go-top` (1001) but below the boot loader (1005) so the old chrome's fixed elements don't visually poke through. **Two more gotchas found the same way (real browser console errors this time), both in shared assets that assume `layout/main`'s sidebar/topcontent always exist — fixed in the shared files themselves, not worked around per-page, since the next fullscreen page would hit them identically:**
- `public/assets/js/script.js` (re-runs every visit, not `data-turbo-permanent`) had two top-level statements that unconditionally grab a DOM element and immediately call a method on it: `new SimpleBar(document.getElementById('app-simple-bar'), ...)` (`#app-simple-bar` is the sidebar's scrollable nav container, from `navbar.blade.php`) and `document.querySelector(".header-dark").addEventListener(...)` (the dark-mode toggle button, from `topcontent.blade.php`). Neither element exists on a `layout/fullscreen` page, and both throw immediately on `null` (`TypeError: null is not an object (evaluating 'this.el.nodeName')` for the first one) — which, since it's a top-level synchronous script, aborts everything *after* that point in the file too. Both are now guarded with a plain `if (el) { ... }` before use — zero behavior change on any `layout/main` page where the elements do exist.
- **Naming collision, not a null check:** `public/assets/js/customFunction.js` (`data-turbo-permanent`, loaded once per session via `footer.blade.php`) declares a global `const formatRupiah = (angka) => ...`. A page's own `@section('script')` block must never also declare a top-level `formatRupiah` (or `Toast`, the other top-level `const` there) — doing so throws `SyntaxError`/`Can't create duplicate variable: 'formatRupiah'` (Chrome vs. Safari wording for the same rule: a `function`/`var` declaration can't share a name with an existing `let`/`const` binding in the same scope) the moment that page's script runs, which aborts that entire script block. `pos/index.blade.php` had exactly this — its own `function formatRupiah(v) { return 'Rp ' + ... }` — removed in favor of the global one (cosmetically slightly different output: `Intl.NumberFormat` gives `"Rp100.000"`, no space, vs. the removed version's `"Rp 100.000"` — matches how the rest of the app already formats Rupiah everywhere else). Before adding a `@section('script')` helper with a generic name, check it's not already one of `customFunction.js`'s globals (`Toast`, `formatRupiah`, `showModal`/`closeModal`/`HoldCloseModal`, `checkboxVal`, `noMinus`/`maxValue`, `timeDiff`/`timeDiffPause`, `openPopup`, `countAge`, `convertMonthYear`, `limitText`, `normalizeWA`/`phoneInput`).

**POS UI (`pos/index.blade.php`) conventions, from the visual redesign:** the product search grid still renders each result as a `.item` div carrying `data-id`/`data-name`/`data-price` — keep that contract if restyling further, since the delegated click handler (`$('main').on('click', '#productResults .item', ...)`) depends on it, not on any specific inner markup. The cart is rendered as "ticket" divs, not a `<table>` — quantity changes go through a stepper calling `updateCartField(idx, 'qty', newValue)` (dropping to 0 auto-removes the line via `removeCartItem`), and per-item discount stays hidden behind a "+ Tambah diskon" link until clicked, so the panel doesn't default to showing a discount field nobody uses. The cash-received/change calculator (shown only when the active payment method's title contains "cash"/"tunai") is a pure client-side convenience — it's never sent in the `checkout` payload, so adding more payment methods needs no backend change, just correct icon/cash-detection in the title string. Sales history was moved into a modal (`#modalRiwayat`) to keep the main screen focused on the transaction itself; **its DataTable is deliberately initialized on the modal's first `shown.bs.modal` event, not on page load** — initializing a DataTable while its container is still `display:none` makes it mis-measure column widths, so subsequent opens just call `.ajax.reload()` + `.columns.adjust()` on the already-created instance instead of re-initializing.

**`.iconoir-*` icons don't center the way a normal font-icon/glyph does — this bit the POS redesign and is worth knowing anywhere else icons get used.** They're a `mask-image` on a `::before` pseudo-element that's `display: block` by default (see `public/assets/vendor/ionio-icon/css/iconoir.css`), not literal text glyphs on a baseline. Two consequences: (1) `text-align: center` on a wrapper does nothing once the icon is `display: block` — a block-level child doesn't center via its parent's `text-align`, it just sits flush left (hit this on an icon-above-text empty-state and on icon+label pill buttons); (2) an icon placed inline next to text (`<i class="iconoir-x"></i> Label`) doesn't share a text baseline with that label, so default inline alignment often looks visibly "off". Fix both the same way, by making the icon+text (or icon+container) relationship `display: flex`/`inline-flex` with `align-items: center` (and `gap` instead of manual `me-1`/`me-2` margins for the spacing) — never rely on `text-align` or baseline alignment for an iconoir icon.

**UI pattern:** every list page follows the same convention — a Blade `index` view renders an empty DataTable, and a sibling `POST .../getList` endpoint returns server-side-processed DataTables JSON. CRUD is done via `store`/`update`/`delete` POST endpoints returning JSON, consumed by SweetAlert2/AJAX in page-specific `<script>` blocks (not components). Follow this pattern when adding new list/CRUD pages rather than introducing a different frontend approach. Report/dashboard pages (`/report`, `/report-finansial`, `/report-klinis`) follow a lighter variant: a date-range filter + "Terapkan" button at the top, ApexCharts for charts, plain `<table>`s (not DataTables) for lists, one `POST .../getXxx` endpoint per card.

**Printing/PDF:** `Controller::viewOrPdf()` (base `Controller` helper) renders an existing print Blade view either as HTML (default) or, with `?pdf=1` in the query string, as a downloadable PDF via `barryvdh/laravel-dompdf` — reuse this instead of building a separate PDF-only view. Print views live under `resources/views/print/*` and are opened via `openPopup()` (a small JS helper, see `footer.blade.php`) from a parent page's `<script>` block, not navigated to directly. **Images inside a print view need a mode-dependent `src`:** `config/dompdf.php` has `enable_remote => false`, so the PDF-rendering path can only load images by local filesystem path (`public_path(...)`), while the plain-HTML browser path needs an actual URL (`url(...)`). Branch on `request()->boolean('pdf')` to pick the right one (see the signature `<img>` in `surat_sehat.blade.php`/`surat_sakit.blade.php`/`surat_rujukan.blade.php`/`consent.blade.php` for the pattern) — a plain `url()` silently renders a broken image in the PDF, and a plain `public_path()` does the same in the browser.

**Simple e-signature (canvas, not certified):** `m_employee.signature_path` holds a doctor's own saved signature (drawn once via a canvas pad, PNG saved to `public/images/signatures/`), captured through `profileController::saveSignature()` and the "Tanda Tangan Saya" modal in `footer.blade.php`/`topcontent.blade.php`. It's deliberately **not** a certified electronic signature (BSrE/Privy) — that needs a real third-party account, same blocker as BPJS/SATUSEHAT. Stored on `Employee`, not `User`, because every print view already joins to `m_employee` via `t_daftarpasien.dokterfk`, not to `m_users`. The same canvas-drawing technique (vanilla pointer events, no JS library) is reused per-event for patient/guardian signatures in the informed-consent flow (`t_informed_consent.signature_path`) — each is a separate `<canvas>` instance, not a shared component.

**Informed consent (`t_informed_consent`):** covers both a one-time general consent and per-procedure consent (`m_tindakan.butuh_consent` flags which procedures need one). The consent text and procedure name are **snapshotted onto the row at signing time** (`isi_consent`, `tindakan_nama`), not referenced live from a template/`m_tindakan` — so editing or deleting a procedure later never rewrites historical consent records. **The consent wording in `PemeriksaanController::CONSENT_TEXT_GENERAL` and the per-procedure template in `saveConsent()` is a draft I wrote myself, not reviewed by a clinician or lawyer** — flag this to the app owner before treating it as legally sufficient.

**Seeders (`database/seeders/`): master data vs. transactional demo data are two deliberately separate concerns, mirroring the `m_*`/`t_*` table-prefix convention.**
- **`MasterDataSeeder`** (called from `DatabaseSeeder`, so it runs on every `migrate --seed`/`composer setup`) fills in master (`m_*`) tables that used to ship empty or nearly empty — `Supplier`, `Tindakan`, `Product` (pharmacy catalog), `JenisPemeriksaanLab`/`JenisPemeriksaanRadiologi` (test catalogs), `RuangPraktek`, `JadwalKerja` — each its own sub-seeder under `database/seeders/Master/`. Master tables that already had a seeder before this (address data, `Klien`, ICD-9/10, product categories/units/satuan, etc. — see `DatabaseSeeder::run()`) weren't touched. Every sub-seeder is idempotent: most just skip entirely if the table already has rows; `TindakanSeeder`/`RuangPraktekSeeder` skip per-row (match on name/code) instead, so re-running after a user has already added their own entries still adds any new ones here without duplicating.
- **`TransactionalSeeder`** is NOT called from `DatabaseSeeder` — run it explicitly (`php artisan db:seed --class=TransactionalSeeder`). It seeds a handful of illustrative `t_*` records (a few `DaftarPasien` visits across different pipeline stages, a stock-in, two POS sales, one `JadwalDokter` + booked `Appointment`, one Rawat Inap admit→discharge cycle) via `database/seeders/Transactional/*DemoSeeder.php`, each calling the **same helper classes the real app uses** (`ProductQtyHelper::stockIn()`, `PosSaleHelper::checkout()`, `TransactionHelper::createTransaction()`, `AppointmentHelper::book()`, `RawatInapHelper::admit()`/`discharge()`) rather than inserting raw rows — so the resulting ledger/stock-lot/billing-status side effects are exactly what the real UI would have produced, not a shortcut that could drift out of sync with the actual business rules. Kept separate from `MasterDataSeeder` on purpose: this is throwaway demo data for seeing features work with real-looking records, not something that belongs in a fresh production/demo setup by default. One subtlety worth knowing if extending it: a full ledger payment via `TransactionHelper::createTransaction()` only ever reaches `statuspembayaran = 'Verifikasi'`, never `'Lunas'` — see the `status`/`statuspembayaran` note elsewhere in this file for why.

**Module placeholder slots:** the seeded `m_modules` table ([0001_01_00_000000_create_modules_table.php](database/migrations/0001_01_00_000000_create_modules_table.php)) originally included several `🔐 Feature Locked` placeholder rows (codes `RPA`/`RPB`/`RPC` under the "Report" group) that were never part of a premium/paywall system — just unused slots reserved for future menus. All three have since been repurposed in-place (name/icon/route updated via a small migration, e.g. [2026_03_04_000000_activate_laporan_module.php](database/migrations/2026_03_04_000000_activate_laporan_module.php)) into real menus rather than creating brand-new `Module` rows. **Before adding a new top-level menu, check for an existing unused/locked module slot to repurpose** rather than inserting a new one — keeps module IDs stable and avoids growing the table unboundedly. Check `Module::where('name', 'like', '%Locked%')` or similar to find any remaining ones (none remain as of this writing — all three `RPA`/`RPB`/`RPC` slots are used).

**Sidebar group header gotcha:** in [navbar.blade.php](resources/views/layout/navbar.blade.php), a `Module` row with `isheader=1` only renders as a direct clickable link when its `group_id` has **zero** other (`isheader=0`) rows — the submenu query explicitly filters `isheader=0`, so the header itself never appears as a listed child. The moment a second module gets added to that same `group_id`, the header silently becomes a non-clickable collapse-toggle label and stops being reachable (this exact bug shipped once: `SET`'s "Setting" module was seeded as a lone header+link, broke the day `LOG`/"Activity Log" was added to its group, fixed by [2026_03_15_000000_fix_setting_menu_group_header.php](database/migrations/2026_03_15_000000_fix_setting_menu_group_header.php)). **Always give a group a dedicated header-only row (`route => '#'`, `isheader => true`) from the start**, even for a single-item group — never make the header row double as the one clickable item, since any future sibling breaks it. "Layanan Lanjutan" (`LY`, group_id 8 — IGD/Lab/Radiologi/Rawat Inap/Surat Keterangan Mandiri) follows this correctly from day one as the reference example. (The previous example here, `SRM`/"Surat Keterangan" — its own single-item group with `SRT`/"Surat Keterangan Mandiri" as the only child — no longer exists: `SRT` was moved into `LY` per request, and `SRM`, left with nothing under it, was deleted outright rather than deactivated — it had route `#` and was never checked by any `checkAccess` middleware, so nothing depended on the row existing. See [2026_03_24_000000_move_surat_keterangan_to_layanan_lanjutan.php](database/migrations/2026_03_24_000000_move_surat_keterangan_to_layanan_lanjutan.php). **Gotcha hit writing that migration:** computing the next `list_no` for a flat position inside a group must filter `isheader=0` first — a group's header row orders itself among *other headers* on an unrelated scale (e.g. `LY`'s own `list_no` is 8, meaning "8th group in the sidebar"), so including it in `max('list_no')` when placing a new sibling inflates the result to a meaningless number instead of the next slot after the last real sibling.)

**Submenu ordering within a sidebar group is driven purely by `Module.list_no` (ascending), ties broken by row insertion order** — `navbar.blade.php`'s submenu query is `orderBy('list_no', 'asc')` with no secondary sort. "Daftar Pasien" (`group_id` 4) is ordered Ruang Tunggu(`DPP`,1) → Rawat Jalan(`DPS`,2) → Control Antrian(`DPA`,3) → Daftar Rawat Inap(`DPR`,4) → **IGD**(`IGD`,5) → Dibatalkan(`DBT`,6), set via [2026_03_21_000000_reorder_daftar_pasien_menu.php](database/migrations/2026_03_21_000000_reorder_daftar_pasien_menu.php) (original Ruang Tunggu→Dibatalkan ordering) and [2026_03_25_000000_move_igd_to_daftar_pasien_menu.php](database/migrations/2026_03_25_000000_move_igd_to_daftar_pasien_menu.php) (moved `IGD` here from "Layanan Lanjutan" in front of `Dibatalkan`) — `Dibatalkan` deliberately last (exception path, not a frequently-reached one), `IGD` deliberately placed before it since it's a normal entry point, and `DPS` renamed from "Sudah Diperiksa" to **"Rawat Jalan"** (also updated on that page's own header text) to read as the outpatient counterpart to "Daftar Rawat Inap" now that both sit in this same group. Reordering an existing group, or moving a module into it from another group, is just an `update()` on `list_no`/`group_id`/`group_name` (plus `name`, if renaming) in a migration — no route/controller/code change needed, since the sidebar always re-reads the `Module` table live and `checkAccess:<CODE>` gates by module *code*, not by which group it's displayed under. **`IGD`'s move out of "Layanan Lanjutan" (`group_id` 8) follows directly from the registration-unification change above it in this file** — once IGD had no registration card of its own left on `/igd`, the IGD queue reads exactly like the other patient-queue screens in "Daftar Pasien" (Ruang Tunggu/Rawat Jalan/Control Antrian/Daftar Rawat Inap) and no longer belongs grouped with Lab/Radiologi/Rawat Inap/Surat Keterangan, which are reached from a later stage of the flow, not from the queue.

**There is no Vite/frontend build step.** The unused `laravel/laravel`-skeleton Vite+Tailwind scaffolding (`vite.config.js`, `resources/css/app.css`, `resources/js/app.js`/`bootstrap.js`, the `@tailwindcss/vite`/`vite`/`axios`/`laravel-vite-plugin` npm deps) has been removed — no Blade view ever referenced it (`@vite(...)` was never used). `package.json` now only declares `concurrently`, used by `composer dev`'s process runner. The actual admin UI (jQuery, DataTables, SweetAlert2, Select2, FilePond, ApexCharts, flatpickr, etc.) is the pre-built Bootstrap template living under `public/assets/`, loaded via plain `<script>`/`<link>` tags in [resources/views/layout/header.blade.php](resources/views/layout/header.blade.php) and [footer.blade.php](resources/views/layout/footer.blade.php) — edit those files directly when changing styling or client behavior. If a real asset pipeline is ever wanted, it'd need to be reintroduced and actually wired into the layout, not resumed from the old scaffolding.

**SPA-like navigation via Turbo Drive (no framework rewrite):** [header.blade.php](resources/views/layout/header.blade.php) loads `@hotwired/turbo` (pinned CDN `<script>`, UMD build), which intercepts same-origin `<a>` clicks and form submits app-wide and swaps `<body>` via fetch instead of a full reload — this is what makes in-app navigation feel instant. `<meta name="turbo-prefetch" content="false">` is set globally because a couple of links are plain GET with a side effect (e.g. `logout`) and must only fire on an actual click, not on hover. Two consequences any future page/script change must respect:
- **Shared library `<script src>` tags in [footer.blade.php](resources/views/layout/footer.blade.php)** (jQuery, Bootstrap, DataTables, Select2, SweetAlert2, ApexCharts, FilePond, flatpickr core, etc.) are marked `id="..." data-turbo-permanent` so Turbo leaves the already-executed tag alone instead of re-inserting/re-running it on every visit — re-running a classic script that declares top-level `let`/`const` a second time throws `SyntaxError: Identifier '...' has already been declared` (the global lexical environment persists for the whole Turbo session, unlike a real page reload). Only mark a shared script permanent if it's pure library/plugin registration with no page-specific DOM binding. `customizer.js`, `script.js`, and `date_picker.js` are deliberately **not** permanent — they reapply the saved theme / rebind nav & sidebar behavior / re-run flatpickr against each page's own elements, so they must re-run on every visit (made safe to do so: their former top-level `let`/`const` are now `var`, and their `$(document).on(...)` delegated handlers — needed because the bound elements live outside `<main>` — are namespaced and cleared with `$(document).off('.nsJs')` at the top of the file before re-registering, since `document` itself is never replaced by Turbo and would otherwise stack duplicate handlers).
- **Any page's own inline `@section('script')` block is normal body content and safely re-runs on every visit to that page** (DataTable/select2/flatpickr re-init against a fresh element each time is fine) — *except* a top-level `let`/`const` declared outside the `$(document).ready()`/`$(function(){})` wrapper, which hits the same redeclaration crash the second time that exact page is visited in one browser session (e.g. a doctor revisiting `pemeriksaan` for a different patient). Use `var` for any page-level state variable or helper function declared outside that wrapper (see `icd/index.blade.php`, `pemeriksaan/index.blade.php`, `supplier/index.blade.php` for the pattern). Likewise, a `$(document).on(...)` delegated handler needed because the target lives outside `<main>` must be namespaced/off-cleared the same way; one delegated to a selector inside `<main>` can just target `$('main')` instead of `$(document)`, since `<main>` *is* replaced every visit (see `product/index.blade.php`, `pos/index.blade.php`). A handful of pages/partials that are **not** reached via a Turbo-driven route — `login`/`license`/`error`/`welcome` (standalone pages, no `@extends('layout/main')`) — still have this same top-level-`let`/`const` pattern and were deliberately left alone; it's a pre-existing, unrelated latent issue there, not something Turbo introduced. **The AJAX-loaded Pemeriksaan tab partials (`pemeriksaan/content/*`, swapped into `#tab-bawah` via `$.ajax` + `.html()`, not a Turbo visit) hit the exact same underlying mechanism** — jQuery's `.html()` executes inserted `<script>` tags via `$.globalEval`, which runs them in the real global scope, so a top-level `const`/`let` there crashes with the same `SyntaxError: Identifier '...' has already been declared` the *second* time a user opens that tab in one visit to the page (e.g. Persetujuan → Odontogram → back to Persetujuan) — and because it's a `SyntaxError`, the **entire script block silently fails to run at all**, which looked like "the history table is empty" rather than an obvious error. Found and fixed once for real (`consent.blade.php`'s top-level `const CONSENT_TEXT_GENERAL` → `var`, user-reported: consent history going blank after switching tabs and back) — at the time, a full audit of every `pemeriksaan/content/*` and `odontogram-field/*` partial found no other top-level `const`/`let`, so this was logged as a one-off rather than a systemic pattern. **That conclusion was wrong — it was only a one-off *within those two directories*; the rest of the app was never actually scanned.** A later user report ("many pages error after I go to another page and come back, but reload is fine") prompted a real whole-`resources/views` sweep (every `<script>` block, tracking brace depth to separate genuinely top-level declarations from ones safely scoped inside a function/handler) and turned up the same bug, unfixed, in several ordinary `layout/main` admin pages that had simply never been checked: `product/index.blade.php` (`let table`, `let isSubmitting`), `receive_order/index.blade.php` (four `const`-assigned arrow functions: `formatDate`/`loadData`/`approveRO`/`hapusRO`), `transaction/index.blade.php` (`let isSubmittingTransaction`), `ruang_praktek/index.blade.php` (`const bgnum`) — all converted to `var`. (The sweep also flagged `public/monitor-antrian.blade.php`, `public/monitor-ruangan.blade.php`, and `public/portal/booking.blade.php`'s own top-level `const`/`let` — left alone on purpose: those pages don't include Turbo at all, and every link to them is `target="_blank"` anyway, so there's no revisit-in-the-same-tab path that would ever re-run their script a second time.)

**A second, different bug surfaced in the same sweep and explains why some of these "error after navigating away and back" reports were about *chart-heavy* pages specifically (the three `/report*` dashboards): a bare `var chartX;` (no initializer) doesn't actually fix anything by itself.** `var` avoids the `SyntaxError` on redeclaration, but a `var chartX;` with no `=` is *only* a hoisting instruction — re-running that exact line on a Turbo revisit has no runtime effect, so `chartX` keeps pointing at the ApexCharts instance from the *previous* visit, bound to a `<div>` Turbo already discarded when it swapped `<main>`. The page's own `if (chartX) { chartX.updateSeries(...) } else { chartX = new ApexCharts(...) }` pattern (meant to avoid recreating the chart on every AJAX refresh within one visit) then takes the "update" branch against that stale, now-disconnected instance and throws inside ApexCharts' own code. Fix is to make the declaration an actual reset, not just a declaration — `var chartX = null;` — so each fresh Turbo visit's script run genuinely clears it and the `if` takes the "create" branch again against the fresh element. Fixed this way in `report/index.blade.php` (`chartOmset`/`chartGender`/`chartUsia`), `report_klinis/index.blade.php` (`chartTrendKunjungan`), `report_finansial/index.blade.php` (`chartRekapPembayaran`), and — same mechanism, a DataTables instance rather than a chart — `pos/index.blade.php`'s `salesTable` (its `shown.bs.modal` handler does the equivalent `if (!salesTable) { init } else { .ajax.reload() }`). **This is the thing to check for in any future "stateful object + `if (instanceVar)` to decide create-vs-reuse" pattern on a `layout/main` or `layout/fullscreen` page**: the declaration must assign a falsy reset value, not just declare the binding, or the check means "was this ever created in this tab's lifetime" instead of the intended "was this created *this visit*."
- Links that must bypass Turbo and force a real full-page load (e.g. navigating from the Turbo-active app into the standalone `login`/`license` pages, which don't share its head/body structure) get `data-turbo="false"` on the `<a>` — see the logout link in `topcontent.blade.php` and the "Perbarui Lisensi" link in `auth-license.blade.php`.

**Patient flow (core domain):** `DaftarPasien` (daily registration/queue entry, linked to `Patient`) moves through waiting room (`RuangTunggu`) → examination (`Pemeriksaan`, covering vital signs, SOAPE notes, `Tindakan` (procedures), `Odontogram`, diagnosis via ICD-9/ICD-10 models, prescriptions `ResepPasien`) → either cancelled (`Dibatalkan`) or completed (`Diperiksa`) → billing (`Billing`/`Payments`/`Transactions`). `Antrian`/`Monitor` controllers drive the public queue-number display board.

**Business logic is concentrated in helper classes under `app/Helpers/`**, not spread across controllers:
- [ProductQtyHelper.php](app/Helpers/ProductQtyHelper.php) — stock mutations (`t_productqty`), receive-order processing, FEFO (first-expired-first-out) stock-out logic. Purchase PPN is a single global rate, not per-item/per-invoice: `Setting` row with `parameter = 'ppn_persen'` (editable from the Setting page), read once per `processReceiveOrder()` call and fed into `updateProductPrices()` to compute `hpp`/`harga_jual`. **Stock Opname / cycle count** (`stockOpnameAdjustTotal()`/`stockOpnameAdjustLots()`) already existed in this helper — locking (`lockForUpdate`), transactional, inserts a `source='opname'` IN/OUT mutation for the physical-vs-system delta rather than overwriting a running total — but had no controller/route/UI wired to it at all until `StockOpnameController` (`/stock-opname`, module `SO`, in the Farmasi sidebar group) was added: a DataTable of every branch's products with their current system stock (`getBalancesByProducts()`) and an "Opname" action per row (SweetAlert qty-fisik prompt → `adjust()` → `stockOpnameAdjustTotal()`), plus a recent-adjustments history panel (`getHistory()`, filtered to `source='opname'` rows via a join back to `m_products.klienfk` — `t_productqty` itself has no `klienfk` column). **Deliberately hardcodes location id 1** rather than building a location picker — `m_productlocations` has a `klienfk` column but was only ever seeded with one global row ("Warehouse", klienfk 1), and no other controller in the app (`ReceiveOrderController` included — see its own commented-out `// 'location_id' => 1,`) exposes a location selector either; a multi-location UI would be new, unprecedented scope, not something this feature needed to invent on its own.
- [TransactionHelper.php](app/Helpers/TransactionHelper.php) — creates ledger-style `Transactions` records (in/out) tied to patients/billing. When `daftarpasien_id` is set, it also writes a `BillingTransaction` row (payment method, `fk_payment`) — see the ledger/typecode note below.
- [PosSaleHelper.php](app/Helpers/PosSaleHelper.php) — pharmacy POS checkout/void orchestration; reuses `ProductQtyHelper::stockOutFefo()` and `TransactionHelper::createTransaction()` rather than duplicating stock/ledger logic. Price always comes from `m_products.harga_jual`, never client input — cashier can only apply a discount.
- [PayrollHelper.php](app/Helpers/PayrollHelper.php) — BPJS Kesehatan/Ketenagakerjaan cap/rate math and PPh21 TER (Tarif Efektif Rata-rata, PMK 168/2023) bracket lookup (`m_ter_brackets`). **The seeded TER table is sourced from a third-party summary, not the official PMK PDF (which is a scanned image) — verify against the real regulation before trusting payroll numbers in production.**
- [AppointmentHelper.php](app/Helpers/AppointmentHelper.php) — generates bookable slots from a doctor's weekly `JadwalDokter` template, books/cancels `Appointment`s, re-validates slot availability right before insert to guard double-booking.
- [DatabaseBackupHelper.php](app/Helpers/DatabaseBackupHelper.php) — pure-PHP SQL dump (no `shell_exec`/`mysqldump`, since shared hosting usually disables that), dialect-aware (MySQL/SQLite), streams via `cursor()` rather than loading tables into memory.
- [SuratMandiriHelper.php](app/Helpers/SuratMandiriHelper.php) — issues a letter (sehat/sakit/rujukan/umum) for someone who is **not** going through an exam visit (`/surat-mandiri`, module `SRT`). Identity fields are free text on `t_surat_mandiri` (not `Patient`/`DaftarPasien`), jenis-specific fields live in a `detail` JSON column, and price is a single flat value from the `patient_surat_keterangan_price` Setting (previously seeded but unused — this feature is what finally reads it). Charges go straight to the ledger via `TransactionHelper::createTransaction()` with **no `daftarpasien_id`** — same "ledger-only, no `BillingTransaction`" pattern as `KSR`/POS, chosen deliberately so this stays unlinked to patient billing. Payment flow matches POS: pick payment method up front, charge immediately on save, no pending/unpaid state (this app has no such state anywhere else either). Doctor lookup (`fk_employee`) is intentionally **not** klienfk-scoped — `m_employee` has no klienfk column (see the HR/payroll multi-branch exception below) — but the letter row itself and its print route are.

All of these are written defensively (manual validation + `InvalidArgumentException`/`RuntimeException`) rather than using Form Requests — follow that existing style when extending them.

**Ledger/typecode convention:** `t_transactions` is the one global ledger (`transaction_type` in/out, `typecode`). Typecodes in use: `BIL` (patient billing payment), `POS` (pharmacy sale), `FKT` (supplier purchase/receive-order payment), `KSR` (manual cashier entry), `SRT` (surat keterangan mandiri — see `SuratMandiriHelper` above). **Payment method (`fk_payment`) is NOT a column on `t_transactions`** — it's only recorded on the per-domain detail row: `t_billingtransactions` for patient billing, `t_possales` for POS sales, `t_surat_mandiri` for surat mandiri. A report or query that needs "which payment method" must join the right detail table, not `t_transactions` directly.

**Biaya Tambahan (`BiayaTambahanController`, `/biaya-tambahan`, module `BTM` in the "Keuangan" sidebar group, next to Billing):** an admin-only way to charge a patient's visit with something that doesn't come from any clinical catalog — "biaya operasi" was the motivating example, but `nama` is deliberately free text, not Jadwal-Operasi-specific, so it covers "etc." too. **Not the same thing as `KSR`** (`TransactionController`'s manual cashier entry) — `KSR` is ledger-only, with no `daftarpasien_id` at all, so it never shows up on any patient's bill; every `t_biaya_tambahan` row is tied to a `daftarpasien_id` and feeds the exact same outstanding-balance calculation as tindakan/diagnosa/lab/radiologi/resep, so it appears on that visit's tagihan and gets paid through the normal Billing flow instead of sitting in an untracked side ledger.
- **Wired into all four billing surfaces, learned as a standing checklist from the resep-dispensing work above** — `BillingStatusHelper::refresh()`, `BillingController::getTagihanList()`, `ReportFinansialController::getPiutang()`, `PortalController::tagihan()` — **plus `RawatInapHelper::calculateBilling()`**, because a charge like a surgery fee can absolutely happen mid-stay for an inpatient, not just an outpatient visit. Same FK-column gotcha as `t_reseppasien`/`t_jadwal_operasi`: `t_biaya_tambahan.daftarpasien_id`, not `fk_daftarpasien` like tindakan/diagnosa/lab/radiologi.
- **Deletable, but guarded once the visit is `'Lunas'`** — `BiayaTambahanController::destroy()` refuses to remove a charge from a visit whose books are already closed (same "don't let a closed bill drift" reasoning as the `markLunas()` guard above), re-running `BillingStatusHelper::refresh()` after a successful delete just like after a successful add, so the visit's `statuspembayaran` never goes stale either direction.
- **Visit picker searches by No. RM/nama/no. registrasi, most recent first** (`getDaftarPasienList()`), excluding only `Dibatalkan` visits — deliberately not restricted to "today's" or "unpaid" visits, since an admin might need to add a charge to a recently-closed visit's bill before it's paid off. A `<datalist>` on the "nama biaya" field suggests a few common presets (Biaya Operasi, Biaya Administrasi, …) without constraining input to a fixed catalog — this is meant to stay a free-text escape hatch, not grow into another master-data table.
- **Also reachable directly from the Pemeriksaan page's own "Biaya Tambahan" tab** (`PemeriksaanController::biayaTambahan()`/`saveBiayaTambahan()`/`deleteBiayaTambahan()`, sibling flat routes `biayatambahan`, `biayatambahan/save`, `biayatambahan/delete/{biayaId}` under `pemeriksaan/pasien/{id}`, same `checkAccess:DPP` + `verifyDaftarPasienBranch` guard as every other tab, not the `BTM` module) — added so a doctor/staff already on a visit doesn't have to leave and re-search for the same patient on the standalone `/biaya-tambahan` admin page just to add a charge like a surgery fee. No visit/patient picker on this tab at all — `daftarpasien_id` is taken from the already-open visit server-side, which is the entire point of the tab existing. `deleteBiayaTambahan($id, $biayaId)` takes a bare `$biayaId` that `verifyDaftarPasienBranch` doesn't cover (same gotcha as the Operasi tab's `$jadwalId` above) — re-verified inline against both `daftarpasien_id` and `klienfk` before deleting. Same Lunas-delete-guard and `BillingStatusHelper::refresh()`-after-every-mutation behavior as `BiayaTambahanController` — both entry points share the one `t_biaya_tambahan` table and billing-surface wiring, this is just a second way in, not a parallel implementation. The standalone `/biaya-tambahan` admin page stays the place to add a charge to a visit nobody currently has open in Pemeriksaan.

**E-resep → dispensing (`ResepDispensingController`, `/verifikasi-resep`, module `VRS` in the Farmasi sidebar group):** before this, a doctor's `t_reseppasien` row written on the Pemeriksaan page's Resep tab was a dead end — it never touched pharmacy stock (POS and resep were two completely disconnected flows) and, worse, **`t_reseppasien.subtotal`/`jasa_racik` never counted toward the patient's bill at all** — `BillingStatusHelper::refresh()`, `BillingController::getTagihanList()`, `ReportFinansialController::getPiutang()`, and `PortalController::tagihan()` all summed tindakan/diagnosa/lab/radiologi but never resep, despite `subtotal` existing on the table specifically for this. **Both gaps are now closed:**
- All four billing surfaces above now also sum `t_reseppasien.subtotal` (which already includes `jasa_racik` for racikan — don't add it again separately). **Watch the FK column name**: `t_reseppasien.daftarpasien_id`, not `fk_daftarpasien` like every other billable table (tindakan/diagnosa/lab/radiologi) — easy to copy-paste wrong. `RawatInapHelper::calculateBilling()` already summed resep correctly before this (it was the one surface that got it right from day one).
- **Dispensing** is a new pharmacist-facing worklist (one row per *visit* with undispensed resep, not per resep line — a visit's resep is handed over as one packet) that calls the same `ProductQtyHelper::stockOutFefo()` POS already uses (`source: 'transaction'`, same bucket) for every non-racik line's `obat_id`×`qty` and every racikan ingredient's `product_id`×`qty` (from `t_reseppasienracikan` — each ingredient's `qty` there is already the *total* consumed for the whole batch, not per-unit, confirmed from the frontend's own subtotal math in `resep.blade.php`), then flips `t_reseppasien.is_processed` (the column already existed, unused, since the table's original migration) + a new `tgl_processed` timestamp. The whole dispense for a visit is one DB transaction — if any single line's stock is insufficient, `stockOutFefo()` throws and the entire visit's dispensing rolls back, never leaving some drugs deducted and others not. A non-racik line with no `obat_id` (doctor wrote a free-text drug name not linked to the product catalog) has nothing to deduct but is still marked processed.
- **`PemeriksaanController::saveOrUpdateResep()` always did (and still does) a destructive replace-all** — soft-delete every active resep row for the visit, insert the doctor's whole current cart fresh — which would silently wipe out rows whose stock has already been deducted the moment a doctor hits Submit again after dispensing. Guarded by rejecting the whole save (400) if any existing active resep row for that visit has `is_processed = true`, with a message telling staff the resep is already verified & dispensed.

**`t_daftarpasien.status` ("Selesai" etc.) and `.statuspembayaran` ("Lunas" etc.) are two independent fields — never gate one on the other.** This used to be conflated: `PemeriksaanController::updateStatus()` only ever set `status = 'Selesai'` once `statuspembayaran` reached `Verifikasi`/`Lunas`, so an exam that was clinically done but unpaid stayed stuck at `'Payment'` forever; symmetrically, `BillingController::processPaid()` refused to record *any* payment once `status == 'Selesai'`, which would have permanently locked out payment the moment the first bug was fixed. Both are now decoupled on purpose: finishing an exam (`f=1` in `updateStatus()`) always sets `status = 'Selesai'` regardless of payment state, and `processPaid()`'s guard checks `statuspembayaran == 'Lunas'` (not `status`) before rejecting a new payment. `RawatInapHelper::discharge()` does the same on the underlying `DaftarPasien` when a patient goes home. None of the billing *list* queries needed to change — `BillingController::getList()` already filtered "belum bayar" via `statuspembayaran`, not `status`. **`updateStatus()` with `f=1` also auto-discharges an active rawat inap admission** for that visit (looks up `RawatInap::where('fk_daftarpasien', ...)->where('status', 'dirawat')` scoped by `klienfk`, then calls `RawatInapHelper::discharge()`) — staff finishing an inpatient's exam on the main Pemeriksaan page ("Selesaikan" button) no longer have to separately open `/rawat-inap` or the Rawat Inap tab just to free the bed; `ringkasan_pulang` is left blank in this path (fill it via the Rawat Inap tab/`/rawat-inap` beforehand if needed). The JSON response carries `admisi_dipulangkan` (bool) so the frontend can show a different success toast when this happened. **Caught while verifying this change:** `tests/Unit/TransactionHelperTest.php`'s `test_full_payment_marks_verifikasi_and_completes_visit` was a stale leftover from *before* this decoupling — it still asserted that a full payment alone sets `status = 'Selesai'`, which `TransactionHelper::createTransaction()` no longer does (that duplicated calculation was already replaced by a call to `BillingStatusHelper::refresh()`, which only ever touches `statuspembayaran`). Renamed to `test_full_payment_marks_verifikasi_without_touching_visit_status` and fixed to assert `status` stays `'Dalam Antrian'`.

**Re-verified on request (rechecking "pay, then add more charges, must detect the new balance"):** `BillingStatusHelper::refresh()` is already called from every charge-adding method in `PemeriksaanController` (`saveTindakan`, `saveDiagnosa`, `saveLab`, `saveRadiologi`, `saveOrUpdateResep`) and from `TransactionHelper::createTransaction()`, so the flow the decoupling above exists for — pay a visit in full, then a doctor adds one more tindakan/resep/etc. to that same visit — already works correctly end to end: `resolve()`'s `$totalPaid + 0.000001 < $totalTagihan` branch fires on the next `refresh()` regardless of what `statusSebelumnya` was, dropping it back to `Verifikasi Sebagian`/`Belum Verifikasi` so the new balance is visible again. Covered by `tests/Unit/BillingStatusHelperTest.php::test_additional_charge_after_full_payment_reopens_the_balance` and `::test_additional_charge_after_lunas_reopens_the_balance`. **A real, separate bug turned up during that recheck, not in the reopening logic itself but in what reads the status it produces:** grepping the whole codebase for anywhere `statuspembayaran` is ever actually *set* to `'Lunas'` turns up nothing — `resolve()` only ever *preserves* `'Lunas'` if a row already carries it (`$statusSebelumnya === 'Lunas' ? 'Lunas' : 'Verifikasi'`), and nothing else in the app (no controller, no helper, `PemeriksaanController::resolvePaymentStatus()` included — a near-identical but **dead**, never-called duplicate of `BillingStatusHelper::resolve()` left over from before that helper was extracted) ever assigns it fresh. A handful of tests hardcode `'statuspembayaran' => 'Lunas'` directly via Eloquent `create()` as fixture setup, which is the only way that value exists anywhere outside the schema's own enum. Practical consequence: a visit paid 100% in full via `BillingController::processPaid()` lands at `'Verifikasi'`, never `'Lunas'`, forever. `BillingController::getList()`'s own "Not Yet" filter already accounts for this correctly (excludes both `'Verifikasi'` and `'Lunas'`), but `ReportFinansialController::getPiutang()` only excluded `'Lunas'` — so every fully-paid visit sat permanently in the "Piutang" (outstanding receivables) report as a phantom Rp 0 row. **Fixed** by filtering `getPiutang()`'s result on the actually-computed `sisa` (`total_tagihan - total_paid`) being `> 0`, not on the status label — correct regardless of whether `'Lunas'` is ever reachable, and resilient to any future overpayment/refund edge case. (Whether `'Lunas'` is ever *meant* to become reachable — e.g. a future manual "close the books" confirmation step distinct from `processPaid()`'s own recording of payment, which is the two-step reading the `'Verifikasi'` vs `'Lunas'` naming implies — is a product decision for the app owner, not assumed/built here.) Covered by `test_piutang_excludes_a_visit_that_is_already_fully_paid`.

**Follow-up, requested explicitly: `'Lunas'` is now reachable.** `BillingController::markLunas()` (`POST billing/mark-lunas/{id}`, same `checkAccess:BL` + klienfk scoping as the rest of `BillingController`) is a deliberate **manual, separate** closing step — not `resolve()` auto-promoting `'Verifikasi'` to `'Lunas'` the moment the balance hits zero. Chosen over auto-promotion because the status name `'Verifikasi'` itself reads as "pending verification," not "done," and collapsing the two would make `'Verifikasi'` permanently unreachable in practice (full payment would skip straight to `'Lunas'`) — the opposite of what the naming implies was intended. It re-derives the current balance server-side via `BillingStatusHelper::refresh()` before closing rather than trusting the client's last-seen `statuspembayaran`, and refuses (400) unless that recompute lands on exactly `'Verifikasi'` (already `'Lunas'` → refuses too, no double-close). Surfaced on `billing/detail.blade.php` as a "Tandai Lunas" button, shown only when the already-loaded tagihan totals leave zero balance *and* the last-fetched `statuspembayaran` (now also returned by `getTagihanList()`, which previously didn't expose it at all) is `'Verifikasi'` — same confirm-then-`Turbo.visit('billing')`-back-to-list pattern `process-paid`'s own submit handler already uses. Since the reopening behavior two paragraphs up already handles a charge added after the fact regardless of prior status, a visit closed as `'Lunas'` and then given a new tindakan correctly drops back out of `'Lunas'` on the next `refresh()` exactly like it would from `'Verifikasi'` — closing it isn't a one-way trap. `PemeriksaanController::resolvePaymentStatus()` (the dead duplicate mentioned above) was deleted outright while in here, since it was confirmed zero-caller and would otherwise be one more place to misread "how does Lunas happen" from.

**BPJS coverage: confirmed there is none, by design-so-far, not by oversight.** `jenispembayaran` (`'UMUM'`/`'BPJS'`, set at registration) is stored and displayed but never read anywhere to affect pricing — grepping the whole `app/` tree for it outside migrations turns up exactly three unconditional writes/selects, zero conditional branches on its value. Every `tindakan`/`obat`/lab/radiologi charge bills the same price regardless of `jenispembayaran`; `m_tindakan` has no coverage/tariff-class column at all, and `m_products.is_fornas` (national drug formulary flag) is stored but likewise never checked against anything. This matches the BPJS integration status noted above (no Vclaim API client, no real credentials) — there's no INA-CBG tariff/coverage mapping to drive a "BPJS covers X, patient pays the difference for Y" computation even if there were, so `jenispembayaran = 'BPJS'` today is purely an informational label on the registration, not a billing rule. Building real coverage logic needs an actual BPJS tariff/coverage reference (per-tindakan class, per-INA-CBG-group for inpatient) sourced from real BPJS documentation/credentials, not guessed — same caution as the rest of this BPJS section.

**Audit trail:** the `LogsActivity` trait ([app/Traits/LogsActivity.php](app/Traits/LogsActivity.php), hooked via `bootLogsActivity()`) is applied to financial/medical models (`DaftarPasien`, `DiagnosaPasien`, `PayrollSlip`, `JadwalKerjaKaryawan`, `Cuti`, etc.) to record create/update/delete history. Apply it to new models in that same risk category rather than adding ad-hoc logging.

**Global helper functions** (`WIB()`, `generateNoRM()`, `countAge()`, `rupiah()`) are autoloaded unconditionally via `composer.json`'s `autoload.files` → [app/Helpers/globalHelper.php](app/Helpers/globalHelper.php). `generateNoRM()` depends on `Auth::user()->klienfk` (multi-tenant client key) to build the patient record number.

**Auth is session-based only** (`config/auth.php` `web` guard, Eloquent `User` provider on table `m_users`). There is no JWT/API guard (`tymon/jwt-auth` was an unused dependency and has been removed) — don't introduce API-token auth assumptions without adding that infrastructure first.

**App-wide license/serial gate:** [app/Http/Middleware/AuthApiMiddleware.php](app/Http/Middleware/AuthApiMiddleware.php) is registered globally (`bootstrap/app.php`) and runs before every request except `license*`/`serialActivation` (note: NOT `login` — reaching the login page itself requires a valid license too). It checks a single-row `serial` table ([app/Models/Serial.php](app/Models/Serial.php)) for a `serial_code`/`valid_until`, re-validates against a remote endpoint (`AUTH_SERVER` env) at most once every 3 hours (tracked via `serial.last_check`), and redirects to the `license` route if missing/expired. The source uses octal-escaped string literals (`"\154\x69..."` etc.) rather than plain strings — when editing this file, decode/verify literal values with PHP rather than guessing (e.g. `php -r 'echo "\154...";'`). Setting `TYPE_LOCAL_SERVER=2` in env bypasses this gate entirely; `tests/Feature/AuthApiMiddlewareTest.php` covers its branches and `phpunit.xml` pins `TYPE_LOCAL_SERVER=0` so tests don't silently inherit a developer's local `.env` value.

**Multi-tenancy / multi-branch (`Klien`):** most domain tables (patients, registrations, transactions, products, receive orders) are scoped by `klienfk` (client/tenant ID) referencing `Klien`, and most queries filter by the logged-in user's `klienfk` — check this when adding new queries so data doesn't leak across branches. `Klien` itself now has a full CRUD UI ([KlienController.php](app/Http/Controllers/Website/KlienController.php), module `CAB`) and users are assigned a branch via a `klienfk` dropdown on the user add/edit form. **Exception: the HR/payroll domain (`m_employee`, `t_payroll_slips`, `t_cuti`, `t_jadwalkerjakaryawan`) has no `klienfk` column at all** — employees, payroll, and leave are global across branches, not tenant-scoped. This is a known gap, not an oversight to "fix" casually; any change here needs a real decision about what multi-branch HR should mean (shared staff pool vs. per-branch).

**Recurring bug pattern — unscoped lookup-by-id — turned out to be systemic, not isolated.** A self-review audit of the new hospital modules found several `findOrFail($id)`/`where('id', $id)` lookups that checked a record existed but never checked it belonged to the caller's `klienfk` — letting a logged-in user from one branch read or modify another branch's data just by sending a different ID, bypassing the UI's own correctly-scoped dropdowns/search. A follow-up full-codebase audit (one controller at a time) found the same gap almost everywhere, at every severity level:
- **`UserListController`** had it on every single method (`getList`, `edit`, `updateData`, `activateUser`/`deactivateUser`, `deleteUser(WithEmployee)`, `resetPass`) — the worst case, since it meant a branch-B admin could list branch-A's staff and overwrite their password (account takeover). All fixed.
- **`PemeriksaanController`** (plus `OdontogramController`, sharing the same route group) had it on every exam tab — vitals, SOAPE, tindakan, diagnosa, resep, cetak surat, consent, lab, radiologi, status. Rather than patch dozens of methods individually (and risk missing one, which is exactly how the Lab/Radiologi/Consent tabs ended up with the same gap the day they were built), this was fixed with **one middleware** — `App\Http\Middleware\VerifyDaftarPasienBranch` (alias `verifyDaftarPasienBranch`), applied once to the `pemeriksaan/pasien/{id}` route group in `routes/web.php`. It decodes the route's `{id}` and checks ownership before any controller code runs, so every current and future method under that group is covered for free. **This is the preferred pattern going forward for any route group keyed by a single tenant-scoped `{id}`** — a group-level middleware beats per-method scoping for exactly this reason.
- **`BillingController`** and **`PatientController`** had it on their edit/update/detail endpoints too (billing collection, patient PII).
- Master-data controllers (`ProductController`, `ICDController`, `TindakanController`, `SupplierController`, `RuangPraktekController`, `JadwalDokterController`) had it on their edit/update/delete/list methods, plus a few related sibling bugs found along the way: `SupplierController::store()` hardcoded `klienfk => 1` for every new supplier regardless of who created it; `TindakanController::saveTindakan()`'s create path never set `klienfk` at all (silently fell through to the column default); `RuangPraktekController::addRoom()`'s "is there a free room" check was global, so branch A having a free room could wrongly block branch B from adding one.

**Any new endpoint that takes a bare `{id}` (route param or request field) and loads/mutates a tenant-scoped model needs an explicit `->where('klienfk', ...)` in that same query** — "the record exists" is not "the record is mine." For a whole route group keyed by one `{id}`, prefer a group-level middleware (see `VerifyDaftarPasienBranch`) over scoping every method by hand.

**BPJS integration status:** `m_setting` has empty placeholder credential fields (`bpjs_vclaim_*`, `bpjs_pcare_*`, `bpjs_antrean_*` — cons_id/secret_key/user_key/base_url, one set per BPJS "New Generation" API service since each is registered separately) added via [2026_03_08_000000_add_bpjs_api_credential_settings.php](database/migrations/2026_03_08_000000_add_bpjs_api_credential_settings.php). **No API client exists yet** — nothing calls these. The app owner doesn't yet have real BPJS credentials; building the HMAC-SHA256-signed client before then would mean shipping untested guesses against undocumented edge cases. `m_pasien.nobpjs` (the card number) is already wired into the patient form independently of this.

**Doctor appointment booking:** `JadwalDokter` (weekly shift template per doctor/room) + `Appointment` (booked slot) under modules `JDD`/`BKG`. Watch the `Appointment.tanggal` cast — it must be `'date:Y-m-d'`, not plain `'date'`, or the double-booking guard's exact-string date comparison silently stops matching (this exact bug has already been hit and fixed once).

**A `RuangPraktek` can be shared by several doctors across different shifts — resolved via `JadwalDokter`, not the room's own `fk_dokter` column.** `m_ruangpraktek.fk_dokter` is a legacy single-doctor-per-room column (still editable from the Ruang Praktek master-data screen) that walk-in registration (`PatientController`) **no longer reads**. Instead, `PatientController::resolveDokter()` (called by the registration form via AJAX whenever the room or registration date/time changes) uses `AppointmentHelper::getDokterOnDuty()` — the reverse of its slot-generation lookup — to match the chosen room against `JadwalDokter`'s day-of-week + time-of-day window: exactly one match auto-fills the doctor, zero or multiple matches fall back to every doctor who has any shift in that room at all, letting staff pick manually (e.g. a covering doctor with no schedule row yet). `processPatient()` still validates the submitted `dokterfk` server-side (must be an active doctor in the same `klienfk`) rather than trusting the client, but does **not** require it to match a specific `JadwalDokter` row — that flexibility is intentional, not a gap, so an unscheduled walk-in covering doctor can still be registered. If a room is never given a `JadwalDokter` row by anyone, `resolveDokter()` returns an empty candidate list rather than silently falling back to the full doctor list — rooms are expected to be set up via the Jadwal Dokter screen, not implicitly.

**The actual place to map several doctors onto one room is the Jadwal Dokter screen (`/jadwal-dokter`, module `JDD`)** — add one row per doctor per room/day/time, same as any other shift. `JadwalDokterController::getRuangPraktekByDokter()` used to filter the room dropdown by `m_ruangpraktek.fk_dokter`, which meant a room already "owned" by one doctor there was invisible to every other doctor's own schedule form — fixed by dropping that filter (it now lists every active room in the branch, since room ownership is no longer single-doctor). `store()`/`update()` also now reject a new shift that literally overlaps another doctor's active shift in the same room/day (`findRoomConflict()`) — a room can be shared across different time slots, just not the same one by two doctors at once.

**The Ruang Praktek master-data screen's "assign one doctor to this room" feature has been removed** (`RuangPraktekController::getDokterList()` deleted, the `roomsdr`/`fk_dokter` field dropped from `updateRoom()`, the select2 doctor picker removed from `ruang_praktek/index.blade.php`, `addRoom()`'s old "block adding a room while another has no doctor yet" check removed since that constraint no longer makes sense) — doctors are managed exclusively through Jadwal Dokter now, so this screen only edits a room's name/code. `m_ruangpraktek.fk_dokter` itself is **not** dropped from the schema (existing rows/tests still reference it) — it's just unread by every current code path; a follow-up migration to drop the column is a separate, more disruptive decision left for later.

Each of `3D_dewasa.blade.php`/`3D_anak.blade.php`/`2D_global.blade.php` fetches this *before* loading any saved marker/chart data (`getDiagnosisList()` → `getDataOdonto()`), since the picker needs the list to resolve colors/labels while rendering.

Pre-existing fragility carried over as-is (the original hardcoded array had the same assumption); fixing it would mean looking up the `is_reset` row dynamically instead of by position.

- **IGD** adds `t_daftarpasien.triase` (enum Merah/Kuning/Hijau/Hitam, nullable). Radiologi is the one 3-stage workflow (`diminta` → `terjadwal` → `selesai`); its result image upload uses `Storage::disk('public')` (`storeAs(..., 'public')`, same convention as `TransactionController`'s attachment upload) — **not** the `public_path('images/...')` pattern used for e-signatures, since that one is a real uploaded file, not a base64 canvas drawing. Its print report follows the same mode-dependent-`src` DomPDF pattern (`Storage::disk('public')->path(...)` for PDF, `Storage::url(...)` for HTML).
- **Rawat Inap** (`RawatInapHelper` + `RawatInapController`) is the one that changes a core assumption: `DaftarPasien` normally models a single same-day visit. An admission (`t_rawatinap`) always points at an existing `DaftarPasien` row (patient already came in through normal registration or IGD) — tindakan/diagnosa/lab/radiologi/resep during the stay are **not** duplicated into rawat-inap-specific tables, they're the same existing Pemeriksaan-tab records keyed to that same `fk_daftarpasien`, just summed up at discharge. `m_kamar`: one row = one bookable bed/room unit (a 3-bed ward is 3 rows), with `status` toggled `kosong`/`terisi` on admit/discharge.   - **Rooms group beds via `m_ruangan_inap` (one row per physical room) → `m_kamar.fk_ruangan`/`nomor_ranjang` (one row per bed within it)**, added once rooms needed to be managed/visualized as a unit ("how many beds does this room have") rather than one bed at a time. `tarif_per_hari`/`kelas` stay mirrored onto every `m_kamar` row from its room — deliberately not moved off `m_kamar` — so `calculateBilling()` and the rest of admit/discharge, which read `$kamar->tarif_per_hari` directly, needed zero changes. `RawatInapHelper::createRuangan()`/`updateRuangan()`/`deleteRuangan()` own this: creating a room with `jumlah_ranjang` generates that many beds; editing a room's rate/class cascades to every bed it owns; growing/shrinking `jumlah_ranjang` adds beds or removes the highest-numbered ones, rejecting the shrink if any bed that would need removing is `terisi`. Pre-existing `m_kamar` rows from before this existed are backfilled into their own 1-bed room by the migration, so nothing is orphaned. The admission form's "pick a room/bed" UI and the room-management screen are the same bed-grid visualization (`RawatInapController::getRuanganList()` → `resources/views/pages/rawat-inap/index.blade.php`), just rendered in two different containers (`selectable` vs. not) from the same cached JSON — clicking an empty bed (green) selects it for admission; clicking an occupied one (red, in the management grid) shows who's in it via a `Swal` popover rather than a modal, so staff can scan many rooms at a glance. All data was already fully loaded into one cached JS array per grid (`ruanganListCache`/`rwiAdmisiCache`/`rwiPindahCache`), so paging is a client-side slice of that array, not a new paginated endpoint.
  - **Mid-stay room transfers (`t_rawatinap_pindah`) happen from the Pemeriksaan page's Rawat Inap tab, not from `/rawat-inap`.** `PemeriksaanController::rawatInap()`/`pindahRuanganRawatInap()`/`rawatInapRuanganList()` — deliberately placed here (same convention as the Lab/Radiologi tabs: flat sibling routes `rawatinap`, `rawatinap/pindah`, `rawatinap/ruanganList` under the `pemeriksaan/pasien/{id}` group, gated by `checkAccess:DPP` + `verifyDaftarPasienBranch`, not the separate `RWI` module) because that's where staff already are while rounding on a specific patient; `/rawat-inap` stays the place for admission/discharge/room setup. `RawatInapHelper::pindahRuangan()` frees the old bed, occupies the new one, and logs the move (old kamar, new kamar, timestamp, note) — reusable in both places (also surfaced read-only from `/rawat-inap`'s admission list via `getPindahLog`, so the log isn't buried inside Pemeriksaan only).
  - **`calculateBilling()`'s room charge is now split across however many rooms were occupied**, via `buildKamarSegments()` reading the transfer log: e.g. 3 days in a regular room then 2 in VIP before discharge bills `3×tarifReguler + 2×tarifVip`, returned as a new `rincian_kamar` breakdown array alongside the (now summed) `biaya_kamar` total. A transfer's calendar day counts entirely toward the room moved **into** — the simplest rule that can't double- or zero-count a day, consistent with this system already billing in whole calendar days. With zero transfers this reduces to exactly the old single-room whole-stay calculation (same `jumlah_hari`/`biaya_kamar` as before), so no-transfer billing is unaffected — verified by the pre-existing tests passing unchanged.

It's a thin wrapper over `RawatInapHelper::admit()` — same validation (rejects a visit that already has an active admission, rejects an occupied room), so no duplicate guard logic. The tab's bed-grid picker for admission (`#modalAdmisiRawatInap` in `pemeriksaan/content/rawat_inap.blade.php`) reuses the same generalized rendering functions (`rwiBedSquare`/`rwiRenderLantaiFilter`/`rwiRenderGrid`) as the transfer picker, parametrized by target input/grid IDs rather than duplicated. - **Carbon 3 gotcha found here:** `diffInDays()` on Laravel 12's Carbon 3 returns a **float**, not an int like Carbon 2 — two timestamps a few microseconds apart (e.g. admit-then-immediately-discharge in a test) produce `1.0000068...`, not `1`. Normalize both sides to `->startOfDay()` before diffing, then `(int) floor(...)`, whenever you need a clean day count.

- **"Monitor Ruangan" (`/monitor/ruangan`, public, no login)** is a TV/corridor-screen room-occupancy board, same `?klienfk=`-scoped no-auth pattern as `MonitorController::antrian()`/Monitor Antrian (defaults to branch 1, no `Auth::user()` available). - **`RuanganOperasiController` (`/ruangan-operasi`, module `OK`) lives in the "Master" sidebar group** (`group_id` 2, alongside Tindakan/ICD/Jadwal Dokter), not "Layanan Lanjutan" — it's a master-data CRUD screen, not a clinical-service module, moved there on request right after first shipping in the wrong group. **`m_ruangan_operasi` deliberately doesn't mirror `m_kamar`/`m_ruangan_inap`'s bed-per-room structure** — one OK room serves one case at a time, so there's no child "bed" table. `status` only flags a room active/`maintenance`; "currently in use" is derived **live** from `t_jadwal_operasi` (`status = 'berlangsung'`), not stored on the room — unlike Rawat Inap, which genuinely needs a stored empty/occupied toggle because a stay lasts days, while an OK room's slot turns over several times a day. A room can't be deleted while it still has an active (`dijadwalkan`/`berlangsung`) schedule — guarded via `withCount`, the same shape of guard Rawat Inap already uses for rooms/beds still occupied.
- **Scheduling happens from a new "Operasi" tab on the Pemeriksaan page** (`PemeriksaanController::operasi()`/`saveOperasi()`/`updateStatusOperasi()`/`cancelOperasi()`, sibling flat routes under `pemeriksaan/pasien/{id}` — `operasi`, `operasi/ruanganList`, `operasi/dokterList`, `operasi/save`, `operasi/status/{jadwalId}`, `operasi/cancel/{jadwalId}` — same `checkAccess:DPP` + `verifyDaftarPasienBranch` guard as every other tab, not a separate module), **not** from a dedicated page — "the doctor schedules the operation" was the explicit request. `fk_pasien` and `fk_daftarpasien` are both taken from the current visit server-side, never from client input, so there's no patient picker on this tab at all — just room, doctor, procedure name, date/time. **One visit can only have one active (`dijadwalkan`/`berlangsung`) schedule at a time** — `saveOperasi()` rejects a second one until the first is cancelled or completed, checked explicitly here since `OperasiHelper::create()` itself doesn't know about "one per visit" (that's a Pemeriksaan-tab-specific rule, not a general scheduling rule). `updateStatusOperasi()`/`cancelOperasi()` take a bare `$jadwalId` that `verifyDaftarPasienBranch` *doesn't* cover (that middleware only checks the route's own `{id}`, i.e. the visit) — both re-verify the schedule actually belongs to this visit and klienfk before acting, via a shared private `findJadwalOperasiForVisit()`. The tab's own modal is mounted/remounted into `document.body` on every AJAX tab-load and disposes its previous Bootstrap instance first — the exact same gotcha and fix already documented for the Rawat Inap tab below, required because `#tab-bawah.html(...)` swaps this partial's markup (including the modal) on every tab click.
- **The calendar is a public, no-login monitor board** (`MonitorController::operasi()`/`operasiData()`, `/monitor/operasi`, plain `GET` — not the POST+CSRF the staff-side AJAX elsewhere uses, since there's no session/CSRF token to send) — same `?klienfk=`-scoped pattern as Monitor Antrian/Monitor Ruangan, linked from "Menu Lain" in `topcontent.blade.php`, no sidebar `Module` row. **Explicitly confirmed with the app owner** (asked directly, same category of decision as Monitor Ruangan's own public-vs-staff-login question) rather than defaulted to — they chose public + showing patient names directly on the calendar, not hidden behind a click. `OperasiHelper::getCalendarEvents()` takes `klienfk` as a plain parameter rather than reading `Auth::user()` (it's also called from `PemeriksaanController`, which does have a session) — exactly the nullsafe-`Auth`-style accommodation `AppointmentHelper::book()` already needed for the same reason (one caller has a session, one doesn't).
- **Calendar view reuses FullCalendar that was already vendored in the template but never actually wired up anywhere** (`public/assets/vendor/fullcalendar/global.js` + `fullcalendar.bundle.css`, ~689KB) — confirmed zero references anywhere in `resources/views/` before this feature; the only prior trace was a dead demo scaffold (`public/assets/js/calendar.js`, hardcoded dummy events, never included by any route). Used as-is rather than adding a new CDN dependency, consistent with the "no build step, pre-built template" approach documented above. Loaded only on `public/monitor-operasi.blade.php` itself, not globally in `footer.blade.php`, so no other page pays for that payload.
- **Monitor Operasi redesigned right after first shipping: room-status cards + live countdown are now the primary (default) view, with the calendar demoted to a secondary "Kalender" tab** — the bare calendar alone didn't scale to "many rooms" (everything merged into one grid) and had no way to show "who's in surgery right now" at a glance, both raised directly by the app owner. `view-switch` toggle (`switchView()`) lazy-inits `FullCalendar.Calendar` only the first time "Kalender" is opened, same "don't measure a `display:none` container" reasoning as the POS sales-history-modal/report-chart gotchas already documented above — this one just applies it to a fresh widget instead of a stale one.
  - **`OperasiHelper::getRoomStatuses($klienfk)`** (new) returns, per room, the in-progress case (`status = 'berlangsung'`, trusting the staff-set status rather than re-deriving "in progress" from a time window — that status is exactly what the Pemeriksaan tab's "Mulai Berlangsung" button exists to set) and the soonest upcoming one today (`status = 'dijadwalkan'`, `jam_mulai >= now`, so a slot that already passed without being started doesn't linger as "next"). One call covers every room, so the monitor needed no separate "list of rooms" endpoint. Exposed publicly via `MonitorController::operasiStatus()` (`/monitor/operasiStatus`, plain `GET`, `?klienfk=`) — deliberately separate from `operasiData()`, which is scoped to whatever date range the calendar widget happens to be showing (could be a different month entirely) and so can't double as "what's happening right now."
  - **Countdown math happens entirely client-side** against data already fetched every 15s — `serverNow()` corrects for the kiosk device's own clock being wrong by diffing against `server_time` in the `operasiStatus` response once per poll, and a `setInterval` every 1s re-renders every visible countdown (room cards + the focus overlay, if open) from that corrected clock plus the cached room-status payload, rather than re-fetching every second. An overrun (now past `jam_selesai` with the case still `berlangsung`, or past `jam_mulai` with the next case still `dijadwalkan`) shows as `overdue` (red) instead of a negative number. **Gotcha avoided, not hit:** the date component of the countdown target is taken from `serverNow()`'s own local year/month/day (`localDateStr()`), not `new Date().toISOString().slice(0,10)` — `toISOString()` converts to UTC first, which is the wrong calendar date for part of the night in WIB (UTC+7); caught in review before shipping, not from a bug report.
  - **Room cards are paged exactly like Monitor Ruangan's room grid** (`ROOMS_PER_PAGE = 6`, `PAGE_CYCLE_MS` auto-advance, pauses while the focus overlay is open) — same reasoning: nobody is standing at this kiosk to click "next page" either. A room-filter pill row (`renderRoomFilter()`/`pilihRuangan()`, same pill styling as Monitor Ruangan's lantai filter) narrows both the card grid and the calendar's event list to one room — answers "lihat jadwal ruangan yang 1" without a separate page.
  - **Clicking a room card opens the same fullscreen-focus pattern Monitor Ruangan already established** (`#focusOverlay`, `position:fixed;inset:0`, Escape or a close button to exit) — here showing the room's current/next case in large type plus the live countdown at `6rem`, legible from across a room. Auto-advance pauses while a focus is open, same as Monitor Ruangan.
- **`app/Helpers/OperasiHelper.php`'s conflict-detection/status-transition logic itself didn't change in either redesign** — still owns conflict detection and status transitions, called from `PemeriksaanController` (write), and now `MonitorController` (read, both `operasiData()` and `operasiStatus()`), matching this app's "business logic in Helper classes, not controllers" convention. Guards both room AND doctor conflicts with the same interval-overlap check `JadwalDokterController::findRoomConflict()` already uses (`mulai < lawan.selesai AND selesai > lawan.mulai`), scoped to a specific `tanggal` rather than a recurring day-of-week — a room can't host two overlapping cases (physically impossible), a doctor can't be scheduled in two rooms on overlapping times either (can't be in two places at once), checked as two separate queries. `status = 'dibatalkan'` rows are excluded from the conflict check (a cancelled slot frees its time for reuse); `reschedule()` re-runs the same check excluding its own row. Status flow: `dijadwalkan` → `berlangsung` → `selesai`, or `dijadwalkan`/`berlangsung` → `dibatalkan` — a `selesai` case can't be cancelled, a `dibatalkan` one can't be rescheduled or have its status changed again. `JadwalOperasi::$casts` sets `'tanggal' => 'date:Y-m-d'` from the start — the exact `Appointment` gotcha already documented above (plain `'date'` round-trips through a full datetime, breaking exact-string conflict lookups) — avoided from the start here rather than rediscovered as a bug.
- **Superseded design, kept here as a pointer so it isn't rediscovered:** the first version of this feature put everything behind a staff-only `/jadwal-operasi` page (module `JOP`) with its own create/edit modal and FullCalendar instance, and `fk_dokter`/`fk_pasien`/room pickers used Select2 AJAX hitting `JadwalOperasiController`. All of that was removed in the same session once the app owner clarified the actual intended flow (schedule from Pemeriksaan, view on a public monitor, master data under Master) — if any of that older shape resurfaces in a stale branch or diff, it's superseded, not a second implementation to reconcile with this one. The monitor's own first cut (bare calendar, no room-status view) was likewise superseded by the room-status-cards-plus-countdown redesign directly above, same session.

**Patient self-service portal (`/portal/*`):** a separate, unauthenticated-by-staff-guard area for patients — no `m_users` account, no `checkAccess` module system. Identity is verified once (No. RM + tanggal lahir match) and tracked via a plain session key (`portal_patient_id`), guarded by the `portal.auth` middleware alias (`App\Http\Middleware\PortalAuth`), not Laravel's `auth` guard. Views live under `resources/views/public/portal/*` as standalone HTML documents (no `@extends('layout/main')`) — same convention as the existing public queue-monitor board — and the booking page is vanilla JS (no jQuery), also matching that convention. `PortalController` methods scope every query to the logged-in patient's own `pasienfk`/`pasien_id`/`fk_pasien` server-side; never trust a patient-supplied ID for whose data to show or whose appointment to cancel. Booking reuses `AppointmentHelper` as-is (see its nullsafe `Auth::user()?->klienfk` — that guard exists specifically so this helper still works when called from a request with no staff session).
